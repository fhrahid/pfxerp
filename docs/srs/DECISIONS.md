# SRS scope and requirement decisions

**Recorded:** 2026-11-07 from the project owner's answers to `audit/open-questions.md`. These decisions define the target SRS. They do not change the audit's source-grounded `IMPLEMENTED` labels or assert deployment behavior. Application code remains outside this documentation phase.

| ID | Decision | Target status and source boundary |
|---|---|---|
| DEC-01 | Use the Next.js console as the primary target interface. Treat the API-served static console as a transitional operational interface until feature parity and deployment usage are verified. Specify shared capabilities once and note which client currently exposes each workflow. | **PROPOSED** product baseline chosen for the SRS. Both clients exist (`frontend/app/page.tsx:13–78`, `frontend/components/shell.tsx:48–67`, `src/main.ts:25–26`, `public/app.js:361–408`). Which one is deployed remains `UNVERIFIED`. |
| DEC-02 | CHRO and CPO are distinct target job-role labels. One person may hold multiple labels. The CEO may assign or revoke any system or newly created label for any person, subject to an audit record. A label alone grants no service access. | **PLANNED** by owner direction. Current `User.role` is a single string and the compiled enum has CPO but no CHRO (`prisma/schema.prisma:14–21`, `:237–250`); role creation exists but multi-role assignment does not (`src/modules/roles/roles.service.ts:70–102`). |
| DEC-03 | Replace fixed role-only authorization with deny-by-default attribute-based access control (ABAC). Evaluate an authenticated person's active CEO-managed service/action grant together with resource ownership or squad relationship, business state and applicable context/conflict rules for every protected operation. The CEO grants and revokes service/action entitlements directly to individuals; descriptive job-role labels alone confer none. Grant scope limits, maker/checker constraints and any CEO emergency exception remain UNVERIFIED. | **PLANNED** target direction, refined by the owner's ABAC preference on 2026-11-07 while retaining the earlier direct-grant decision. Current guards check fixed role names and services perform selected ownership checks (`src/common/guards/roles.guard.ts:15–33`, `src/modules/tasks/tasks.service.ts:413–480`). No general ABAC policy implementation is evidenced in `package.json:22–54` or `src/app.module.ts:78–83`. [NIST SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final) defines ABAC as evaluating subject, object, operation and sometimes environment attributes against policy. |
| DEC-04 | Define one versioned notice envelope for both web clients and the server: X25519 key agreement, HKDF-SHA-256, AES-256-GCM, fields `version`, `alg`, `ephemPk`, `iv`, `data` and `tag`. Base64 `data` contains ciphertext only; base64 `tag` contains the 16-byte authentication tag. Preserve Ed25519 signatures over recipient, title, category and exact envelope. Reject unknown versions/algorithms. | **PLANNED** normalization of a **PARTIAL** feature. Both clients currently put ciphertext and tag together in `data`; the server checks `alg`, key type, `iv` and `data` length but does not require a separate `tag` (`src/modules/notices/notices.controller.ts:55–70`, `frontend/lib/notice-crypto.ts:74–89`, `public/app.js:2547–2562`). Dispatch failure is not established by this difference. `src/common/crypto/e2ee.util.ts:30–54` shows a separate-tag Node envelope. |
| DEC-05 | Use the **local PostgreSQL database specified by `.env.example`** as the physical schema baseline for the SRS, per the owner's clarification. Reconcile it with `prisma/schema.prisma` and both migrations. Treat any separate deployed environment as `UNVERIFIED` until inspected. | **IMPLEMENTED local schema evidence:** read-only catalog queries found 43 application tables, 30 enums and both migrations finished; model columns and enum values match Prisma's current model (see `docs/srs/audit/database-baseline.md`; source: `.env.example:10–13`, `prisma/schema.prisma:1–10`, `prisma/migrations/20261107000000_align_schema/migration.sql:1–120`). |
| DEC-06 | Require all-or-nothing execution of a sprint payout batch: either every ranked squad's ledger movement and payout status commit together, or none do. A retry with the same idempotency key must not pay a squad twice. | **PROPOSED** interpretation of the owner's request for a suitable company rule. Current code posts one squad at a time and changes the batch status afterward (`src/modules/sprint-payouts/sprint-payouts.service.ts:108–190`); `README.md:81` overstates atomicity. Plain-language example: if the fourth squad's posting fails, the first three must not remain paid while the payout stays unfinished. |
| DEC-07 | Keep Redis, BullMQ, TimescaleDB, policy-engine tooling, and Cloudflare R2 backup capabilities as **future requirements**, with explicit deployment/migration acceptance criteria. A named library is a design option unless the capability truly depends on it. | **PLANNED** by owner direction; these appear in plans (`plan/main.md:38–58`, `plan/cto.md:795–812`, `plan/other.md:57–130`) but are not present in current runtime manifests (`package.json:22–54`, `docker-compose.yml:1–52`). For other tasks, accept a relevant artifact, link or written outcome and require PM/appropriate reviewer approval. Do not infer progress solely from commit counts. | **PLANNED** by owner direction. Do not quote the README's old pass count as proof of present behavior. | **UNVERIFIED** current runtime status. The old result is at `README.md:111–129`; scripts exist but were not run in the source audit (`scripts/full-verify.mjs:1–7`). |

## Requirement drafting consequences

- Place identity, membership, authorization, notices, ledger and task evidence in shared requirements. Reference each from CHRO, CPO, CTO, CFO, PM and Developer sections without duplicating the same obligation.
- Keep current behavior and target behavior separate. A source-backed capability may be `IMPLEMENTED` while its requested replacement is `PLANNED` or `PROPOSED`.
- For DEC-02/03, specify separate job-role assignment and direct per-person grants as subject entitlements within the ABAC policy. Check subject, action, resource and context attributes at each policy decision point. CEO ability to assign a job-role label does not imply service access or an override of resource safeguards.
- For DEC-04/06/08, write testable acceptance criteria from the chosen contract. Include migration/compatibility handling for existing notices, payout retries and older tasks without evidence-type metadata.
- A separate deployed schema and current verification results remain evidence gaps. The local database is the agreed physical baseline for this SRS; do not extrapolate its state to another deployment.
